thuida/backend/commerce-engine -- updating catalogs

This covers two different kinds of change: adding a new FIELD to the
existing schema (like material was added), and adding a new
RETAILER. Each touches a different, specific set of files. The
relevant comments already live in the files themselves -- this is a
single place that ties them together and tells you which files to
open, in order.

===============================================================================
ADDING A NEW FIELD (worked example: material)
===============================================================================

Four files, always in this order. All four are mechanical, one-line
additions -- nothing here should require thinking hard, just care
about getting the column INDEX right.

-------------------------------------------------------------------------
1. common-lisp/throughput/impact-parser.lisp -- find the real index
-------------------------------------------------------------------------

Every field starts here, because you need to know which column
number the Impact Radius (IR) feed actually puts it at. Impact.com
standardizes this layout across every retailer on the network, so
the index is the same for ONP, SinoCrafted, Terra, and any future
retailer -- verify it ONCE against a real row, not per-retailer.

To check a real index (don't trust memory -- verify it):

    sbcl --non-interactive --load common-lisp/retailers/onp/onp-db.lisp \
         --eval '(print (get-indices (car *onp-impact-rows*)))'

The FIRST row of a raw catalog is the header row -- (car ...), not
(second ...) -- it prints every column name paired with its index
directly from the real feed. material showed up at index 26,
between color (25) and size (27) -- confirmed this way, not assumed.

Two edits in this file:

    (defconstant +color+ 25)
    (defconstant +material+ 26)     <- add here, in index order
    (defconstant +size+ 27)

    :color (nil-if-blank (nth +color+ row))
    :material (nil-if-blank (nth +material+ row))    <- add here, in row->product

-------------------------------------------------------------------------
2. common-lisp/product.lisp -- add the struct slot
-------------------------------------------------------------------------

In (defstruct product ...), add the new slot near related fields:

    color             ; i.e, "Natural"
    material          <- add here

-------------------------------------------------------------------------
3. common-lisp/product.lisp -- add the database column
-------------------------------------------------------------------------

Same file, in *products-columns* -- this is what actually generates
the CREATE TABLE and INSERT statements, so this is the step that
makes the column exist in the database at all:

    (list "color" "TEXT" #'product-color)
    (list "material" "TEXT" #'product-material)    <- add here

-------------------------------------------------------------------------
4. Rebuild the database -- schema changed, this is not optional
-------------------------------------------------------------------------

CREATE TABLE IF NOT EXISTS is a no-op against an existing table --
adding a column here does NOT retroactively add it to your current
database/impact.db. Delete and rebuild:

    rm database/impact.db
    bash shell/update-onp.sh

If update-onp.sh reports every retailer as "already up to date" and
skips the reload (this happens if nothing actually changed on
Impact's end since your last sync), that's not good enough after a
schema change -- force it directly instead:

    sbcl --non-interactive --load common-lisp/retailers/onp/onp-db.lisp \
         --eval '(load-products-to-db *products*)'
    sbcl --non-interactive --load common-lisp/retailers/catalogs.lisp \
         --eval '(load-all-generic-catalogs)'

-------------------------------------------------------------------------
If the field needs to be searchable/filterable on the frontend too
-------------------------------------------------------------------------

That's a SEPARATE step, in a different codebase entirely --
frontend/db-accessor.lisp's *display-columns* (add the column name
so it flows into every product plist automatically) and, if it
should be a facet filter like brand/color/retailer,
frontend/search.lisp's *fts-columns*/*fts-source-columns* (so it's
also indexed for full-text search) plus a *-counts wrapper function
and a render-filter-section call in frontend/components/
filter-panel.lisp. This is genuinely more work than adding the field
itself -- worth doing only once you actually want to filter by it.


===============================================================================
ADDING A NEW RETAILER
===============================================================================

Two genuinely different cases, and they're NOT interchangeable --
picking the wrong one means duplicating work or missing something.

-------------------------------------------------------------------------
Case A: no custom parsing needed (most retailers)
-------------------------------------------------------------------------

If the retailer's Impact Radius feed can be read with nothing beyond
"pull the standard columns" -- no special quantity extraction, no
retailer-specific naming quirks to untangle -- this is the easy
case. Two files:

    common-lisp/retailers/catalogs.lisp
        Add one (defparameter *newretailer-catalog* ...) for its
        file path, and one (defun load-newretailer () ...), matching
        the existing SinoCrafted/Terra pattern. The file's own top
        comment walks through this in full.

    shell/update-onp.sh
        Add one line to the GENERIC_RETAILERS array:
        "advertiserId|Display Name|dir-name|load-fn"
        The script's own top comment explains exactly how to find
        the advertiserId (query catalogs_info_file.xml -- do NOT use
        <name>, it's not guaranteed unique across retailers).

That's the whole cost. No directory needs to exist beforehand
(sync_catalog creates it), no other file needs to change.

-------------------------------------------------------------------------
Case B: needs custom parsing (like ONP's quantity extraction)
-------------------------------------------------------------------------

If the retailer needs retailer-specific logic -- ONP's product names
embed size/quantity information ("16 oz", "Case of 24") that has to
be extracted with retailer-tuned regex, which wouldn't generalize to
any other retailer's naming conventions -- it needs its own
dedicated wrapper file, not an entry in catalogs.lisp.

    common-lisp/retailers/<newretailer>/<newretailer>-db.lisp
        Use common-lisp/retailers/onp/onp-db.lisp as the template.
        Copy its overall shape: self-locating path setup, loading
        impact-parser.lisp, retailer-specific catalog path, retailer-
        specific extraction function(s), and a load-<retailer>
        function following the same calling convention as the
        generic retailers' load-* functions.

    shell/update-onp.sh
        Its own sync_catalog call(s), near ONP's -- in the "CUSTOM
        RETAILERS" section at the top of the script, NOT
        GENERIC_RETAILERS. The script's own top comment covers this
        case too.


===============================================================================
AFTER ANY CHANGE
===============================================================================

Full re-test, same as always -- see RUNBOOK.txt in this same
directory for the complete "run everything" / "check the database" /
"reload one retailer" command reference.
